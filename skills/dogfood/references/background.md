# Background runs

Create a native scheduled task only as part of authorized installation or when the user requests a schedule. The build package itself does not create a live schedule. Reuse an existing Dogfood task when its identity is known. Do not create duplicates.

Resolve the durable store identity, source skill, and permitted projects before constructing the task. Use the host's actual scheduling tool schema. The default proposal is daily in the user's local time; select the actual time during setup. Do not require recurring review of routine changes.

Save this task instruction with the installation's concrete identifiers:

> Use Dogfood. Read the configured durable installation settings and findings. Honor pause state and existing permissions. Review past evidence, select pending improvements that still apply, and claim work before editing. Apply and verify at most three improvements within 20 minutes. Preserve unrelated edits, record actual versions and check results, and keep a reversal method. Recheck the remote lease before every external write. Checkpoint unfinished work and its resume condition. Report completed changes, pending activation, and blocked items. Do not create another scheduled task or recursive run.

The final saved prompt must contain real store and skill references, never placeholders. On web runtimes, ensure both remain available without the current workspace. On desktop, verify that local projects remain accessible and the required machine and app are running.

Test the prompt interactively on a small isolated fixture first. A successful manual test proves the workflow only. Record scheduler execution as unverified until an actual unattended run succeeds. If the host offers no supported scheduler, preserve the task prompt and record background execution as blocked.
